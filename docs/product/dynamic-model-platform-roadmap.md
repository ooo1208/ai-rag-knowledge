# 动态模型平台产品路线图

> 当前实现状态：Phase 0 和 Phase 1 的核心代码已完成，Phase 2 已完成数据库模型目录、动态客户端、连接测试、MCP 工具目录和固定联网搜索的第一版链路；基础设施层已补上公网出站 URL 校验边界。详情见 [`project-status.md`](./project-status.md)。管理员配置、权限、搜索缓存/审计和 MCP 执行仍未完成。

## 1. 产品目标

将当前“配置文件中固定模型 + Ollama/OpenAI 两套接口”的 RAG 应用，逐步升级为：

- 管理员可以配置多个模型服务商；
- 系统可以发现、缓存和管理可用模型；
- 用户在一个统一聊天入口选择模型；
- 普通聊天、流式聊天和 RAG 聊天走同一套模型解析链路；
- 聊天模型、Embedding 模型和后续 Rerank 模型相互独立；
- 后续可以安全地支持用户自带 API Key、用量统计和模型路由。

## 2. 产品边界

### 首期支持

- 系统预置 Ollama；
- 系统预置 OpenAI 兼容服务；
- DeepSeek 作为预置服务商模板；
- PostgreSQL 保存连接、模型和配置；
- Redis 只用于缓存和短期状态；
- 统一的流式聊天接口；
- RAG 按知识库标签检索。
- MCP 工具以服务端白名单方式绑定到模型预设；联网能力只能通过受控的只读搜索入口或工具进入。

### 首期不支持

- 普通用户直接上传 API Key；
- 多模型并行对比；
- 自动按成本和质量智能路由；
- 计费和充值；
- 任意第三方协议的无限适配。
- 聊天请求传入任意 URL、API Key、STDIO 命令或未经审批的写工具。

## 3. 核心概念

### ProviderConnection

服务商连接，表示“如何访问一个模型服务”。例如 DeepSeek、Ollama、本地 OpenAI Compatible 服务。

关键字段：

- `id`
- `providerType`
- `name`
- `baseUrl`
- `credentialRef`
- `ownerType` / `ownerId`
- `enabled`
- `status`
- `lastCheckedAt`

### ModelBinding

连接下的一个实际模型。例如 `deepseek-chat`、`qwen2.5:7b`。

关键字段：

- `id`
- `connectionId`
- `upstreamModelId`
- `displayName`
- `capabilities`
- `contextWindow`
- `enabled`
- `source`
- `lastSyncedAt`

### ModelPreset

给用户使用的模型配置。它可以绑定一个模型，并保存温度、最大输出长度、系统提示词、是否启用 RAG 等参数。

对外暴露的 `modelConfigId` 应该指向这一层，而不是直接暴露第三方模型 ID。

### McpServerConnection / McpTool

`McpServerConnection` 表示已登记的 MCP 传输连接，`McpTool` 表示该连接同步出的工具。
`model_preset_tool` 再把工具绑定到具体模型预设，前端只能看到稳定 `toolId` 和安全摘要，
不能看到 endpoint、凭证引用或 STDIO 命令。

公网联网暂时不作为任意 URL 抓取能力提供，而是通过固定 provider 的 `SEARCH_ONLY` 工具接入。
所有 HTTP 出站地址必须先通过 `OutboundUrlValidator`，并在重定向、响应大小和超时层再次限制。

### EmbeddingProfile

知识库使用的向量模型配置。它与聊天模型独立，切换 Embedding 模型时必须记录版本和向量维度。

## 4. 分阶段实施计划

## Phase 0：产品和技术基线

### 目标

建立统一模型抽象，冻结第一版 API 和数据模型。

### 工作内容

1. 明确 ProviderConnection、ModelBinding、ModelPreset、EmbeddingProfile 的数据结构。
2. 确认统一聊天接口：

```http
POST /api/v1/chat
POST /api/v1/chat/stream
```

请求至少包含：

```json
{
  "modelConfigId": "mc_xxx",
  "message": "问题内容",
  "ragTag": "知识库标签",
  "conversationId": "可选",
  "webSearch": false
}
```

3. 统一错误码、流式响应格式和模型能力枚举。
4. 明确 `modelConfigId` 的历史可追溯规则：会话创建后保存实际模型配置快照。
5. 补齐当前接口缺失的显式 `@RequestParam`，避免依赖编译器是否保留参数名。

### 验收标准

- 能画出从 `modelConfigId` 到实际服务商请求的完整链路；
- 同一个请求结构可以表达 Ollama、DeepSeek 和 OpenAI 兼容服务；
- RAG 不再直接依赖某个 Controller 中的具体模型 Bean；
- 完成 API 和字段文档后才进入 Phase 1。

## Phase 1：统一模型调用层

### 目标

先解决代码结构问题，让 Ollama 和 OpenAI 走统一服务，而不改变用户配置方式。

### 工作内容

1. 新增 `ChatModelProvider` 或等价的适配器接口。
2. 实现 Ollama 适配器。
3. 实现 OpenAI 兼容适配器。
4. 把普通聊天、流式聊天和 RAG 聊天统一到一个 Application Service。
5. 保留旧接口作为兼容层，但内部转发到统一服务。
6. 统一流式响应为前端可稳定解析的 SSE 或 NDJSON 格式。
7. 统一超时、异常、空响应和上游错误处理。

### 验收标准

- Ollama 和 OpenAI 都能通过统一接口完成普通聊天和流式聊天；
- 两者都能完成 RAG 流式问答；
- 前端不需要知道使用的是哪个 Controller；
- 上游错误能返回统一错误码和可读提示；
- 旧接口行为没有被破坏。

## Phase 2：管理员模型配置

### 目标

把硬编码配置迁移到数据库，由管理员管理服务商连接和可用模型。

### 工作内容

1. 增加 ProviderConnection、ModelBinding、ModelPreset 表。
2. 将 DeepSeek、Ollama、OpenAI Compatible 做成系统预置模板。
3. 增加连接测试接口（第一版已完成，管理员权限和启用前强制校验待补）。
4. 增加启用、禁用、删除和更新连接能力。
5. 支持手动添加模型 ID。
6. 模型 ID 与展示名称分离。
7. 保存密钥时采用加密或外部 Secret 引用，不允许明文回显。
8. 聊天客户端不再把 `application-dev.yml` 中的模型名称作为唯一运行时来源；配置文件仍可作为系统预置数据的种子。
9. 增加 MCP server/tool 目录和模型预设绑定；只读工具选择 API 第一版已完成。

### 验收标准

- 管理员不改配置文件即可新增一个 OpenAI 兼容服务；
- 连接测试成功后可以添加并启用一个模型；
- 删除或禁用连接后，用户无法继续选择该连接下的模型；
- API Key 在数据库、日志和接口响应中都不会明文出现；
- 服务重启后配置仍然有效。
- 模型选择器可以读取已绑定的 MCP 工具摘要，但不会得到任何密钥或任意连接地址。

## Phase 3：模型发现和模型选择器

### 目标

让模型配置从“手工录入”升级为“自动发现 + 手工白名单”。

### 工作内容

1. 支持服务商模型列表同步。
2. 支持服务商不提供模型列表时手动填写模型 ID。
3. 增加模型列表缓存、刷新时间和同步状态。
4. 支持模型白名单，避免把几千个模型直接展示给用户。
5. 增加模型能力标签：文本、图片、工具调用、Embedding、RAG。
6. 前端按服务商分组、支持搜索、收藏和最近使用。
7. 模型不可用时给出明确原因，不要静默从列表中消失。

### 验收标准

- DeepSeek 和 Ollama 可以自动同步模型；
- 不支持模型发现的服务商仍可以手工添加模型；
- 模型选择器在模型数量增加后仍可搜索和使用；
- 用户可以看出模型属于哪个服务商、是否本地、是否支持 RAG；
- 模型同步失败不会阻塞已有模型聊天。

联网搜索和 MCP 执行的补充约束：

- 搜索先固定服务端 provider，结果必须标记为不可信上下文；
- MCP 连接只能从数据库稳定 ID 解析，不能由请求携带 URL 或命令；
- 远程 HTTP、SSE 和 Streamable HTTP 连接遵守公网/管理员 host allowlist、超时、响应大小和重定向策略；
- STDIO 只运行系统预配置命令，写工具需要显式确认和审计。

## Phase 4：Embedding 和 RAG 产品化

### 目标

把当前全局 Embedding 配置改成可管理的知识库级配置。

### 工作内容

1. 将聊天模型和 Embedding 模型完全拆开。
2. 每个知识库记录 Embedding 模型、维度和版本。
3. 新增 EmbeddingProfile 管理。
4. 知识库创建时固定 Embedding 配置。
5. Embedding 配置变更时禁止直接混用旧向量，要求重建索引。
6. RAG 检索增加 topK、相似度阈值和元数据过滤配置。
7. 明确提示用户：云端模型会接收哪些知识库内容。

### 验收标准

- 聊天模型切换不会破坏已有知识库；
- 不同知识库可以使用不同 Embedding 配置；
- Embedding 模型变更有明确的重建流程；
- RAG 结果可以追踪到知识库、文档和模型版本。

## Phase 5：用户自定义 API Key（BYOK）

### 目标

在已有用户、权限、审计和限流基础上，安全支持用户自带模型服务。

### 前置条件

- 已有用户和租户体系；
- 已有权限模型；
- 已有用量记录；
- 已有限流和并发控制；
- 已有密钥加密和轮换机制；
- 已有 SSRF 防护；
- 已有数据出境提示。

### 工作内容

1. 用户级 ProviderConnection。
2. 加密保存 API Key 或保存 Secret 引用。
3. 用户只能访问自己的连接。
4. 支持测试、禁用、删除和轮换。
5. 支持自定义模型白名单。
6. 增加每用户调用次数、Token 和错误统计。
7. 支持每用户并发、额度和速率限制。
8. 记录模型实际调用来源和费用归属。

### 验收标准

- 用户无法读取其他用户的 Key 或模型连接；
- 删除 Key 后新的请求立即失效；
- 连接异常、超额、限流都有清晰的用户提示；
- 管理员可以审计连接创建、使用和删除记录；
- 不允许通过自定义 URL 访问受保护内网资源。

## Phase 6：运营能力和智能路由

### 目标

在真实调用数据基础上，增加稳定性、成本和体验优化。

### 工作内容

1. 失败重试和备用模型。
2. 按模型能力路由简单问题和复杂问题。
3. 统计延迟、成功率、Token、成本和用户满意度。
4. 支持模型下线、迁移和兼容别名。
5. 支持管理员设置默认模型和租户级策略。
6. 支持多模型对比，但明确提示用户会产生多次调用成本。

### 验收标准

- 路由规则可解释、可关闭、可审计；
- fallback 不会导致 RAG 上下文丢失；
- 模型下线有迁移方案；
- 成本和调用来源可追踪到用户、会话和模型。

## 5. 推荐开发顺序

```text
Phase 0 产品和技术基线
    ↓
Phase 1 统一模型调用层
    ↓
Phase 2 管理员模型配置
    ↓
Phase 3 模型发现和选择器
    ↓
Phase 4 Embedding 与 RAG 产品化
    ↓
Phase 5 用户 BYOK
    ↓
Phase 6 路由、成本和运营
```

每完成一个阶段，都必须满足该阶段的验收标准，才进入下一阶段。不能先做前端模型下拉框，再反过来补模型权限、密钥和数据模型。

## 6. 第一版成功标准

第一版不追求支持所有模型，而是满足以下闭环：

1. 管理员配置一个 Ollama 和一个 DeepSeek 连接；
2. 系统能够同步或手动录入模型；
3. 用户在一个选择器中看到两个服务商的模型；
4. 用户通过同一个聊天接口完成普通聊天和 RAG 聊天；
5. 会话记录实际使用的模型配置；
6. API Key 不明文存储、不出现在日志和响应中；
7. 一个服务商暂时不可用时，用户可以看到明确错误；
8. Embedding 配置不会因为聊天模型切换而被意外改变。

达到这个闭环，项目才具备继续扩展用户 BYOK、计费和智能路由的基础。
